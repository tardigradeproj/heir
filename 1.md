# Proposal: `WorkerJoinToken` CRD + controller

Automate `heir token generate --kubeconfig ./heir-kubeconfig.yaml --expiry 3h` as a
declarative Kubernetes resource, reconciled by a new controller alongside
`RuntimeReconciler`.

## 1. Problem

Today, joining a worker node to a tenant cluster requires an operator to run, by hand:

```
heir token generate --kubeconfig ./heir-kubeconfig.yaml --expiry 3h
```

This CLI command (`pkg/cmd/token/generate`, `pkg/token/create.go`):

1. Generates a random bootstrap token (`id.secret`).
2. Connects to the **tenant** cluster (the hosted control plane managed by a `Runtime`
   object) using the admin kubeconfig passed via `--kubeconfig`. In practice that file is
   the `<runtime>-kubeconfig` Secret produced by `RuntimeReconciler.setupClientKubeconfig`
   / `GenerateClientKubeconfigAuthSecret` (`pkg/runtime/pki_auth.go`), downloaded to disk
   by the operator.
3. Creates a `bootstrap-token-<id>` Secret of type `bootstrap.kubernetes.io/token` in
   `kube-system` **on the tenant cluster**, with an `expiration` timestamp.
4. Reads the tenant cluster's external API server address from the node-profile
   ConfigMap and builds a bootstrap kubeconfig (CA + address + token), base64-encoded,
   printed to stdout.
5. The operator copies that value onto the new worker node, which uses it
   (`pkg/provision/worker/join.go`, `pkg/provision/worker/bootstrap`) to perform the k8s
   CSR-based TLS bootstrap already automated by `pkg/masteragent/csr_approver.go`.

This is a manual, one-shot, imperative step with no automation hook: it can't be driven
by GitOps, a provisioning pipeline, or autoscaling, and nothing rotates or revokes the
token declaratively.

## 2. Goals

- Let a `WorkerJoinToken` custom resource, created in the **management cluster**
  (same cluster/namespace as the `Runtime` it targets), produce the same artifact the
  CLI prints today: a bootstrap-token Secret on the tenant cluster + a bootstrap
  kubeconfig, without operator interaction.
- Make the bootstrap kubeconfig available as a Secret in the management cluster so a
  provisioning pipeline (e.g. a machine-controller, cloud-init render step, or `kubectl
  get secret -o jsonpath=...`) can consume it the same way the CLI's stdout is consumed
  today.
- Support expiry, surfaced on the object's status, so consumers know when a minted
  token/kubeconfig stops being usable. Expiry is terminal: once TTL elapses the
  controller does **not** mint a replacement on its own (see §3 non-goals) — the
  `WorkerJoinToken` simply goes `Expired` and stays that way.
- Support revocation: deleting the `WorkerJoinToken` deletes the corresponding
  `bootstrap-token-<id>` Secret on the tenant cluster too, not just stops tracking it —
  the token stops working immediately rather than lingering until its natural TTL.

## 3. Non-goals

- Replacing the CLI. `heir token generate` remains for interactive/manual use; the CRD
  is for automated/repeated issuance.
- Changing the worker-side join flow or the CSR auto-approval flow — both are reused
  as-is.
- Enforcing single-use tokens. Kubernetes bootstrap tokens are inherently reusable
  until deletion/expiry; that semantic carries over unchanged.
- Renewing or rotating a token automatically once its TTL elapses. Expiry is a
  one-way transition in v1: the controller never re-mints on its own, whether or not
  the `WorkerJoinToken` object is still present. Getting a working token again always
  requires an explicit action — edit `spec.ttl` (§5 step 4) or delete/recreate the
  object.

## 4. API

New Kind in the existing group/version, `controlplane.tardigrade.runtime.io/v1alpha1`
(`api/v1alpha1/workerjointoken_types.go`), following the conventions already used by
`Runtime` (`api/v1alpha1/runtime_types.go`): `metav1.Condition` status list,
`+kubebuilder:object:root=true` / `+kubebuilder:subresource:status`.

```go
// WorkerJoinTokenSpec defines the desired state of WorkerJoinToken.
type WorkerJoinTokenSpec struct {
	// RuntimeRef names the Runtime (tenant control plane) this token grants access
	// to join. Must exist in the same namespace as this WorkerJoinToken.
	// +required
	RuntimeRef corev1.LocalObjectReference `json:"runtimeRef"`

	// TTL is how long a minted token remains valid on the tenant cluster, starting
	// from the moment it is issued or re-issued.
	// +kubebuilder:default="3h"
	TTL metav1.Duration `json:"ttl,omitempty"`
}

// WorkerJoinTokenStatus defines the observed state of WorkerJoinToken.
type WorkerJoinTokenStatus struct {
	// Conditions reflect the current status. Standard types:
	//   Ready   — a non-expired token and kubeconfig Secret are available.
	//   Degraded — the controller could not reach the tenant cluster or mint a token.
	// +listType=map
	// +listMapKey=type
	// +optional
	Conditions []metav1.Condition `json:"conditions,omitempty"`

	// TokenID is the public identifier of the currently issued bootstrap token (the
	// secret half is never surfaced on the object itself, only inside SecretRef).
	// +optional
	TokenID string `json:"tokenID,omitempty"`

	// ExpiresAt is when the currently issued token expires on the tenant cluster.
	// +optional
	ExpiresAt *metav1.Time `json:"expiresAt,omitempty"`

	// SecretRef names the Secret, in this object's namespace, holding the
	// base64-encoded bootstrap kubeconfig under key "kubeconfig". Owned by this
	// WorkerJoinToken; garbage-collected alongside it.
	// +optional
	SecretRef *corev1.LocalObjectReference `json:"secretRef,omitempty"`
}

// +kubebuilder:object:root=true
// +kubebuilder:subresource:status
type WorkerJoinToken struct {
	metav1.TypeMeta   `json:",inline"`
	metav1.ObjectMeta `json:"metadata,omitzero"`

	// +required
	Spec WorkerJoinTokenSpec `json:"spec"`
	// +optional
	Status WorkerJoinTokenStatus `json:"status,omitzero"`
}
```

### Example

```yaml
apiVersion: controlplane.tardigrade.runtime.io/v1alpha1
kind: WorkerJoinToken
metadata:
  name: pool-a
  namespace: tenant-foo
spec:
  runtimeRef:
    name: tenant-foo
  ttl: 3h
```

```yaml
status:
  tokenID: a1b2c3
  expiresAt: "2026-07-24T18:00:00Z"
  secretRef:
    name: pool-a-join-kubeconfig
  conditions:
    - type: Ready
      status: "True"
      reason: TokenIssued
```

## 5. Controller

New `WorkerJoinTokenReconciler` in `internal/controller/`, registered in `cmd/main.go`
next to `RuntimeReconciler`. Reconcile loop:

1. Fetch `WorkerJoinToken`; resolve `spec.runtimeRef` → `Runtime` in the same namespace.
   If missing, set `Degraded`/`RuntimeNotFound`, requeue.
2. Fetch the `<runtime>-kubeconfig` Secret already reconciled by
   `RuntimeReconciler.setupClientKubeconfig`. If absent (control plane not ready yet),
   set `Degraded`/`RuntimeNotReady`, requeue — this makes `WorkerJoinToken` naturally
   wait on `Runtime`'s own `Available` condition without an explicit dependency.
3. Build a `*kubernetes.Clientset` for the tenant cluster from those raw kubeconfig
   bytes (new helper, see §6), update server url on kubeconfig to reference the internal dns
   fmt.Sprintf("%s.%s.svc.cluster.local", runtime.Name, runtime.Namespace) — this is the cross-cluster client the reconciler
   operates through for the rest of the loop.
4. Decide whether to mint:
   - No `status.expiresAt` yet (first reconcile) → mint.
   - `spec.ttl` changed since the last mint → mint again, treating the edit as an
     explicit request for a fresh token (this is the only supported way to get a new
     token short of deleting and recreating the object — this resource is
     intentionally one-shot, not auto-rotating; see §3 non-goals).
   - Otherwise → no-op; just refresh the `Ready`/`Expired` condition against
     `status.expiresAt` and requeue at `expiresAt` so the condition flips once it lapses.
     Past that point the loop keeps flipping the condition on every reconcile but never
     mints again on its own — `status.tokenID`/`status.secretRef` keep pointing at the
     now-expired token/kubeconfig until the object is edited or deleted.
5. **Mint** (reusing `pkg/token`, see §6 refactor): generate a token, create the
   `bootstrap-token-<id>` Secret on the tenant cluster via the clientset from step 3,
   update server url on kubeconfig to reference the internal dns
   fmt.Sprintf("%s.%s.svc.cluster.local", runtime.Name, runtime.Namespace).
6. Write/update a Secret in the **management cluster**, in the `WorkerJoinToken`'s
   namespace, named e.g. `<name>-join-kubeconfig`, holding the kubeconfig bytes under
   key `kubeconfig`, with `ctrl.SetControllerReference` back to the `WorkerJoinToken`.
7. If step 4 minted a replacement for an existing `status.tokenID` (a `spec.ttl` edit),
   best-effort delete the **previous** `bootstrap-token-<old-id>` Secret on the tenant
   cluster after the new one is confirmed written, so the old token doesn't linger.
8. Update `status.tokenID`, `status.expiresAt`, `status.secretRef`, `Ready` condition.

### Deletion / revocation

Add a finalizer (`controlplane.tardigrade.runtime.io/worker-join-token`). On delete,
before removing the finalizer: rebuild the tenant-cluster clientset (same as step 2–3)
and delete `bootstrap-token-<status.tokenID>` there, best-effort (log and proceed if the
tenant cluster or Secret is already gone — e.g. `Runtime` was deleted first). This is
what makes revocation immediate rather than waiting on Kubernetes' built-in
`TokenCleaner` to reap it at natural expiry.

Deleting the `WorkerJoinToken` therefore always deletes the tenant-cluster Secret too —
there is no supported way to delete just the CRD and leave the underlying bootstrap
token behind. Combined with the no-auto-renew rule above, a `WorkerJoinToken`'s
lifecycle is strictly: `Ready` → (TTL elapses) → `Expired`, permanently, until either
`spec.ttl` is edited or the object itself is deleted (which also revokes the token).

## 6. Required refactor of `pkg/token`

`token.CreateBootstrapToken` currently takes a `kubeconfig` file path + context name and
builds its own `clientcmd.ClientConfig` (via `pkg/k8s.BuildClientConfig`). The controller
has the tenant kubeconfig as bytes already in memory (from the `<runtime>-kubeconfig`
Secret) — it should not round-trip through disk. Proposed split:

- `pkg/k8s`: add `BuildClientFromBytes(raw []byte) (*kubernetes.Clientset, []byte /* caData */, string /* server */, error)`
  using `clientcmd.RESTConfigFromKubeConfig` + `clientcmd.Load`, so both CLI and
  controller share the same CA/server-extraction logic instead of duplicating
  `extractClusterInfo`.
- `pkg/token`: split `CreateBootstrapToken` into a thin CLI-facing wrapper (unchanged
  signature, unchanged behavior) plus a lower-level `IssueBootstrapToken(ctx, client
  kubernetes.Interface, caData []byte, apiServerAddress string, expiry time.Duration)
  (Token, []byte /* kubeconfig */, error)` that both the CLI wrapper and the new
  controller call. `Generate`, `NewSecret`, `buildBootstrapKubeconfig`,
  `readAPIServerAddressFromNodeProfileConfigMap` are already client-agnostic
  (`kubernetes.Interface`) and need no changes.

This mirrors the split already done for cert/kubeconfig validation in this repo
(`pkg/pki/validation.go`, `pkg/util/validation.go`): shared logic factored out, thin
call-site-specific wrappers on top.

## 7. RBAC

New markers on `WorkerJoinTokenReconciler.Reconcile`:

```go
// +kubebuilder:rbac:groups=controlplane.tardigrade.runtime.io,resources=workerjointokens,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=controlplane.tardigrade.runtime.io,resources=workerjointokens/status,verbs=get;update;patch
// +kubebuilder:rbac:groups=controlplane.tardigrade.runtime.io,resources=workerjointokens/finalizers,verbs=update
// +kubebuilder:rbac:groups="",resources=secrets,verbs=get;list;watch;create;update;delete
```

Note the management-cluster RBAC only covers reading the `<runtime>-kubeconfig` Secret
and writing the join-kubeconfig Secret — it does **not** grant any tenant-cluster RBAC,
because the controller authenticates to the tenant cluster as the tenant's own
`system:masters` admin (the same credential `heir token generate` uses today), not as
itself. This is a meaningful trust boundary worth calling out in review: the controller's
ServiceAccount effectively gains cluster-admin on every tenant cluster it can read a
`-kubeconfig` Secret for.

## 8. Alternatives considered

- **Use native `TokenRequest`/CSR bootstrapping instead of the k8s bootstrap-token
  Secret mechanism.** Rejected for this proposal: the worker-side join flow
  (`pkg/provision/worker/bootstrap`) and the CSR auto-approver
  (`pkg/masteragent/csr_approver.go`) are already built around the bootstrap-token +
  CSR handshake and work today; changing the token-issuance mechanism without changing
  the consumer would be a bigger, riskier change than this proposal's scope.
- **Single combined field instead of `SecretRef`, e.g. put the kubeconfig directly in
  `.status`.** Rejected: `.status` is watched/cached broadly and is not meant to hold
  secret material; a dedicated Secret matches how `Runtime` itself already stores PKI
  material and admin kubeconfigs.
- **Auto-rotation via a `renewBefore`-style field, minting a replacement before
  expiry without an explicit `spec.ttl` edit.** Rejected for v1 to keep scope and
  blast radius small (see §5, §6). Nothing about the API shape below precludes adding
  it later as a new optional field.

## 9. Open questions

1. Should the join-kubeconfig Secret be namespaced per-`WorkerJoinToken` (as drafted) or
   should there be a `spec.secretName` override for callers that want a stable, known
   name to reference from a provisioning pipeline before the object is even reconciled?
2. Multiple `WorkerJoinToken`s can target the same `Runtime` (e.g. one per worker pool) —
   confirm that's desired rather than enforcing a 1:1 relationship.
    Answer: A single Runtime can have multiple WorkerJoinToken 
3. Cross-cluster client construction (§6) is new to this codebase — worth a design
   review of its own regarding timeouts/retries if the tenant API server is briefly
   unreachable, so a transient blip doesn't wrongly trigger `Degraded` + event spam.
